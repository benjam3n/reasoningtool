# /dd What are all the dimensions along which thinking tools can vary?
**Date:** 2026-03-09
**Skill:** /dd (Dimension Discovery)

---

**Interpretation selected: 3 — Find all ways something varies.** The user is asking "what are all the ways thinking tools could differ?" about a concept — they want to see the full shape of the variation. Context: this is being applied to the reasoningtool project's 592 structured thinking skills, so "thinking tool" means a structured procedure that guides reasoning.

## Step 1: Seed with Examples

```
EXAMPLES FOR: Thinking tools (structured reasoning procedures)

1.  /rca (Root Cause Analysis) — Traces symptoms back to causes using 5-whys, fishbone, fault trees
2.  /araw (Assume Right / Assume Wrong) — Stress-tests claims by exploring what follows if true vs. what breaks if false

11. /but (Contrast and Objection Handler) — Separates claim from objection, classifies tension type, routes to resolution
12. /dys (Dystopia Analysis) — Constructs worst-case scenarios to reveal risks and warning signs
13. /alt (Abstraction Level) — Adjusts zoom level (concrete vs. abstract) for understanding, deciding, or communicating
14. /soph (Sophisticated Analysis) — Multi-layered reasoning with cross-domain synthesis and second-order effects
```

## Step 4: Domain-Specific Dimensions

Beyond the universal dimensions, here are the dimensions unique to thinking tools:

### Dimension 1: Cognitive Operation
- **What it captures:** The fundamental mental move the tool asks you to make.
- **Possible values:** Decompose, compare, invert (assume opposite), enumerate, simulate (imagine scenarios), synthesize, classify/route, reframe, generate, evaluate, prioritize, trace (follow causal chains), formalize (make precise), operationalize (make actionable)
- **Why it matters:** This is the atomic unit of what a thinking tool does. Two tools might address the same domain but use entirely different cognitive operations.

### Dimension 2: Input Type
- **What it captures:** What the user brings to the tool.
- **Possible values:** Claim/proposition, decision/choice, problem/symptom, goal/desire, emotion/feeling, question, idea/concept, artifact/work product, list/set, vague unease, domain topic, another skill's output
- **Why it matters:** Determines which tool is appropriate. The first routing decision in most orchestrators is "what kind of input is this?"

### Dimension 3: Output Type
- **What it captures:** What the tool produces.
- **Possible values:** Verdict/judgment, recommendation/action plan, structured analysis, generated content/artifact, reframed understanding, list/enumeration, probability estimate, routing decision (to another skill), ranked options, root cause, dimensions/framework, questions to ask, narrative/story
- **Why it matters:** Users care about what they get. Some need an answer; others need a framework; others need content.

### Dimension 4: Epistemic Posture
- **What it captures:** The tool's relationship to truth and the user's position.
- **Possible values:** Adversarial (tries to break the input), supportive (tries to strengthen it), neutral/balanced (explores both sides), generative (creates new possibilities), diagnostic (finds what's wrong), validating (confirms or disconfirms)
- **Why it matters:** /stc is adversarial. /steelman is supportive. /araw is balanced. /ma is generative. The posture determines whether the tool is trying to confirm, deny, or expand.

### Dimension 5: Architectural Role
- **What it captures:** How the tool fits into the skill system as a whole.
- **Possible values:** Router/orchestrator (classifies and delegates), terminal skill (does the work itself), modifier/wrapper (adjusts another skill's behavior), meta-skill (operates on skills themselves), chained skill (designed to feed into specific next skills), standalone (works in isolation)
- **Why it matters:** This is the structural dimension — how skills compose. /claim is a router. /rca is terminal. /ezy is a modifier. /certainty is a chainer. /imps is meta.

### Dimension 6: Depth / Exhaustiveness
- **What it captures:** How deep or thorough the tool goes.
- **Possible values:** Quick/shallow (1x), standard (2x), deep (4x), exhaustive (8x), maximum (16x), adaptive (adjusts based on findings), fixed (one depth only)
- **Why it matters:** The depth scaling system (1x-16x) is a core feature of many skills. Some skills have explicit depth tables; others run at fixed depth. /certainty escalates until resolution. /ezy deliberately compresses.

### Dimension 7: Meta-Level
- **What it captures:** Whether the tool operates on the problem itself or on the thinking about the problem.
- **Possible values:** Object-level (operates directly on the problem), meta-level (operates on how you're thinking about the problem), meta-meta-level (operates on the skill system itself)
- **Why it matters:** /alt adjusts abstraction level (meta). /rca analyzes the problem (object). /imps improves skills (meta-meta). This is the difference between "solve this" and "am I solving this the right way?"

### Dimension 8: Temporal Orientation
- **What it captures:** Which direction in time the tool looks.
- **Possible values:** Backward/retrospective (trace what happened), present/diagnostic (understand current state), forward/prospective (predict or plan), atemporal (timeless analysis)
- **Why it matters:** /rca looks backward. /dys looks forward. /pbr looks forward probabilistically. /dd is atemporal. The temporal direction shapes what kind of insight you get.

### Dimension 9: User State Assumption
- **What it captures:** What emotional/cognitive state the tool assumes or accommodates in the user.
- **Possible values:** Overwhelmed, stuck, curious, confident, uncertain, emotionally loaded, expert-seeking-rigor, beginner-seeking-clarity, biased (and needs correction), state-agnostic
- **Why it matters:** /ezy assumes overwhelm. /soph assumes hunger for depth. /emotion assumes affect. /araw has explicit "corruption pre-inoculation" for when the user is over-validating. The assumed user state shapes tone, complexity, and pacing.

### Dimension 10: Formality of Method
- **What it captures:** How rigidly structured the tool's procedure is.
- **Possible values:** Strict algorithm (follow exactly), structured heuristic (follow the pattern, adapt details), guided exploration (questions to answer, no fixed order), free-form with guardrails, pure routing logic
- **Why it matters:** /pbr is nearly algorithmic (base rates → evidence → likelihood ratios → update). /soph is a structured heuristic. /emotion is guided exploration. /meta is pure routing. The formality determines how much the tool constrains vs. guides.

### Dimension 11: Interpretation Handling
- **What it captures:** Whether and how the tool handles ambiguous input.
- **Possible values:** Multiple explicit interpretations (asks or auto-selects), single interpretation (assumes one meaning), interpretation-free (works regardless of meaning), routes to disambiguation skill
- **Why it matters:** Many skills open with 3 interpretations and a disambiguation question. Some don't. This is a structural design choice about how the tool enters its procedure.

### Dimension 12: Composability Direction
- **What it captures:** What skills this tool feeds into or receives from.
- **Possible values:** Upstream feeder (produces input for other skills, e.g., /dd → /se), downstream consumer (takes output from other skills), bidirectional (chains both ways), isolated (neither feeds nor consumes), hub (many connections)
- **Why it matters:** /dd is designed to feed into /se. /claim routes to /araw. /certainty consumes everything. The dependency graph of skills is a real structural property.

### Dimension 13: Falsifiability / Self-Correction
- **What it captures:** Whether the tool has built-in checks against its own failure modes.
- **Possible values:** Self-checking (validates its own output), corruption-aware (detects user-induced bias), has explicit failure modes listed, has quality checklist, no self-correction mechanism
- **Why it matters:** /araw has "corruption pre-inoculation." /dd has a quality checklist. /soph warns that forced complexity is a failure mode. Some tools are naive — they have no mechanism to detect when they're producing bad output.

### Dimension 14: Domain Specificity
- **What it captures:** How tied the tool is to a particular subject area.
- **Possible values:** Universal (works on anything), domain-flexible (works on most things with adaptation), domain-specific (designed for a particular field), context-dependent (needs domain knowledge to function)
- **Why it matters:** Most skills in the toolkit are universal, but some (like /api or /dbg) are domain-specific. The universality determines how broadly the tool can be applied.

### Dimension 15: Plurality of Output
- **What it captures:** Whether the tool converges on one answer or preserves multiple.
- **Possible values:** Convergent (produces single answer/recommendation), divergent (produces multiple options), both (diverge then converge), preserves-tension (maintains multiple valid answers without forcing resolution)
- **Why it matters:** /dcp converges on a decision. /se diverges into a list. /araw preserves tension between AR and AW findings. /but explicitly asks whether the tension should resolve or be navigated. This affects whether the user gets closure or options.

### Dimension 16: Scope of Change
- **What it captures:** What the tool changes in the user's mind.
- **Possible values:** Adds information, changes belief, changes frame/perspective, changes emotional state, changes action plan, changes the question itself, changes nothing (confirms current state)
- **Why it matters:** Some tools inform (/lr). Some reframe (/alt, /iaw). Some motivate action (/ata). Some change how you feel (/emotion). The type of change is what the user actually gets from using the tool.

## Step 5: Validate Independence

```
INDEPENDENCE CHECK:

- Cognitive Operation vs. Epistemic Posture: Can operation vary while posture stays constant?
  → YES. Decomposition can be adversarial (/stc decomposes to attack) or neutral (/rca decomposes to understand). Independent.

- Input Type vs. Output Type: Can input vary while output stays constant?
  → YES. Both /claim (input: proposition) and /evaluate (input: work product) can produce a verdict. Independent.

- Depth vs. Formality of Method: Can depth vary while formality stays constant?
  → YES. /araw at 2x and /araw at 16x have the same structure but different depth. Independent.

- Architectural Role vs. Meta-Level: Can role vary while meta-level stays constant?
  → YES. /claim (router) and /rca (terminal) both operate at object level. Independent.

- User State Assumption vs. Depth: Can user state vary while depth stays constant?
  → YES. /soph and /pbr both go deep but assume different user states. Independent.

- Temporal Orientation vs. Epistemic Posture: Can temporal direction vary while posture stays constant?
  → YES. Adversarial can be backward (/rca in adversarial mode) or forward (/dys). Independent.

- Interpretation Handling vs. Formality: Potentially correlated — more formal tools tend to have more explicit interpretations.
  → PARTIAL correlation but not identity. /pbr is formal but has no interpretation phase. /emotion has interpretations but is loosely structured. Keep both.

- Domain Specificity vs. Cognitive Operation: Can domain vary while operation stays constant?
  → YES. Decomposition works in any domain. Independent.

- Composability Direction vs. Architectural Role: Correlated — routers tend to be hubs, terminal skills tend to be downstream.
  → MODERATE correlation. But a terminal skill can be upstream (/dd is terminal but feeds /se). Keep both — they capture different things (system role vs. connection pattern).

- Plurality of Output vs. Epistemic Posture: Can plurality vary while posture stays constant?
  → YES. Adversarial tools can converge (single strongest counter) or diverge (all attack vectors). Independent.

- Scope of Change vs. Output Type: Can scope of change vary while output stays constant?
  → YES. Two tools can both produce a "recommendation" but one changes your beliefs while another changes your action plan. Independent.

All 16 dimensions pass the independence check (some with noted partial correlations that don't warrant merging).
```

## Notes and Caveats

1. **These dimensions describe individual tools, not tool systems.** Additional dimensions emerge at the system level: how tools compose, dependency topology, coverage gaps, redundancy patterns, and skill discovery pathways. A full analysis of the 592-skill toolkit as a *system* would need dimensions like "graph centrality," "coverage overlap with other skills," and "discovery friction."

2. **Some dimensions are continuous, not categorical.** Depth (Dimension 6) and Formality (Dimension 10) are more like spectra than discrete categories. The listed values are anchor points, not exhaustive bins.

3. **Dimension 5 (Architectural Role) and Dimension 12 (Composability Direction) are partially correlated** — routers tend to be hubs, terminal skills tend to be endpoints. They remain separate because they capture different things: role is what the skill *is*; composability is how it *connects*.

4. **Dimension 9 (User State Assumption) is often implicit.** Many skills don't declare their assumed user state, but it's visible in design choices: vocabulary complexity, number of steps, tone, amount of scaffolding.

5. **The most useful dimensions for toolkit design are probably 1, 2, 3, 5, and 7.** These five determine the core architecture: what cognitive operation, on what input, producing what output, in what system role, at what meta-level. The others are important modifiers but less load-bearing for structural decisions.

6. **Missing dimension candidate: Cultural/philosophical tradition.** Some tools come from specific intellectual traditions — Bayesian reasoning, design thinking, Socratic questioning, CBT, systems dynamics. This could be a 17th dimension, but it correlates fairly heavily with Cognitive Operation and might not add independent variation.

7. **Missing dimension candidate: Interaction pattern.** Some tools are monologue (tool runs, produces output). Others are dialogue (tool asks questions, user responds, tool adapts). Others are iterative (run, check, run again). This is partially captured by Formality but could be its own axis.
